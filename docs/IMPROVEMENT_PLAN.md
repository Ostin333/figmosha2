# План покращення Figmosha 2

Статус: чернетка, 2026-10-10. Базова версія: 2.3.0.

## Стан виконання (гілка `improvement-plan`, 2026-10-10)

| Фаза | Стан |
|---|---|
| 0 Бенчмарк | інструменти готові (`bench/`); прогони потребують людини з Figma й Claude Code |
| 1 Безпека | зроблено; черга обмежена 64, а не 16 (наявний стрес-тест — 50 агентів) |
| 2 Безпечні записи | зроблено; `mutated` — best-effort (`null`, якщо плагін не бачить змін документа) |
| 3 `run`, `args`, вивід, AGENTS.md | зроблено; AGENTS.md 89 рядків / 5,5 KB |
| 4 DS-хелпери | зроблено, власна реалізація (код southleft не копіювався); перевірено на заглушці Figma, живий `tests/live_ds.py` не запускався |
| 5 Skills | 8 skills (додано `figmosha-history`); Codex: `~/.agents/skills` за офіційною документацією |
| 6 Нові файли | `figmosha new` через `figma.new` — експериментально, не перевірено в Figma Desktop |
| 7 REST | read-only: versions, comments, images; `link`, `figma-token` |
| 8 MCP | `mcp_server.py`, 3 інструменти |
| 9 3.0.0 | не зроблено: обов'язковий токен вмикається після бенчмарку і рішення про реліз |

## Мета

Зробити Figmosha найефективнішим за токенами способом для AI-агента створювати й редагувати дизайн
у Figma, зокрема будувати дизайн-системи (змінні, стилі, компоненти, варіанти), і закрити дірки в безпеці.

Цільові метрики (перевіряються у фазі 0 і фазі 9):

| Метрика | Зараз (оцінка) | Ціль |
|---|---|---|
| Постійні токени в контексті агента (AGENTS.md + описи) | ~5,5k (AGENTS.md 21,7 KB) | ≤ 1,5k + описи skills ~2k |
| Токени на сценарій «колекція кольорів Light/Dark, 20 змінних» | невідомо | ≤ 3k, 1–2 виклики |
| Токени на сценарій «Button, 4 варіанти × 3 розміри, прив'язка до змінних» | невідомо | ≤ 6k, ≤ 3 виклики |
| Хто може виконати код у Figma | будь-який локальний процес; ймовірно веб-сторінка через WS | лише той, хто знає токен |

Принципи, яких тримаємося в усіх фазах:

1. **Агент не читає код, який не мусить писати.** Готові скрипти запускаються за назвою з JSON-аргументами;
   агент пише лише JSON-специфікацію.
2. **Відповідь мінімальна за замовчуванням.** Id, назви, лічильники. Повні дерева — тільки на запит.
3. **Кожна операція запису ідемпотентна** (upsert за назвою), щоб повтор після помилки чи 504 був безпечним.
4. **Одна фаза — один реліз** за правилами з AGENTS.md (semver, CHANGELOG, тег).

## Фаза 1. Безпека: автентифікація і ліміти → 2.4.0 (м'який режим), 3.0.0 (обов'язковий)

Закриває знахідки аудиту: WS-підключення з `Origin: null` від будь-якої сторінки, HTTP без автентифікації,
DoS без лімітів, лог у `/tmp`.

### 1.1 Токен бриджу

1. `bridge.py`: при старті читати токен з `$FIGMOSHA_TOKEN`, інакше з `~/.figmosha/token`;
   якщо файлу немає — згенерувати `secrets.token_urlsafe(32)`, створити каталог `0700`, файл `0600`.
2. Перевіряти токен у `_guard` для `/exec`, `/clear`, `/targets`, `/status`:
   заголовок `Authorization: Bearer <token>`. Порівняння — `hmac.compare_digest`.
   `/` (root) лишити відкритим, але без даних про файли.
3. WS `/plugin`: з'єднання приймається, але до валідного `hello` з полем `token` воно не потрапляє в `PLUGINS`,
   не бачить `peers` і не отримує `exec`. Невалідний або відсутній токен протягом 5 с → закрити з кодом 4401.
4. `figmosha.py`: автоматично читати токен тим самим шляхом і додавати заголовок; нова команда
   `figmosha token` — друкує токен і копіює в буфер (`pbcopy` / `clip` / `xclip`).
5. Плагін (`plugin/ui.html`, `plugin/code.js`):
   - зберігати токен у `figma.clientStorage` (ключ `figmosha-token`), передавати в `hello`;
   - якщо токена немає або бридж відповів 4401 — показати в барі поле «Вставте токен (figmosha token)»;
   - токен ніколи не логувати й не повертати в `result`.
6. М'який режим у 2.4.0: без токена запит виконується, але відповідь містить `notice`
   «токен не передано, з 3.0.0 буде 401». У 3.0.0 — 401. Прапорець `--insecure-no-token` для тестів.
7. `figmosha doctor`: перевіряє наявність токена, права файлу, що плагін автентифікований.

### 1.2 Прибрати підштовхування до небезпечних дій

1. `bridge.py:736-741`: прибрати з тексту 409 пораду `"force": true`; лишити «зачекайте або `/clear`».
2. `/clear` і `force` пишуть в лог, хто (`agent`) і коли їх викликав.

### 1.3 Ліміти (DoS)

1. Максимум 32 live-з'єднання плагінів; понад це — відмова з кодом 4429.
2. Максимум 16 очікувачів у черзі одного документа → 503 `queue full` (нічого не виконано).
3. `MAX_SECONDS` 3600 → 600; більше — лише з `--allow-long`.
4. Rate-limit на `hello`: не частіше 5/с з одного з'єднання.

### 1.4 Файли та дозволи

1. `start-bridge.sh`: лог і pid у `${XDG_STATE_HOME:-$HOME/.local/state}/figmosha/`, `umask 077`,
   перевірка, що pid-файл належить поточному користувачу, перед `kill`. Те саме для `start-bridge.ps1`
   (`$env:LOCALAPPDATA\figmosha`).
2. `plugin/code.js:411`: перевірка URL оновлення — префікс із завершальним `/`.
3. `plugin/manifest.json`: сам плагін не використовує `currentuser`, `activeusers`, `fileusers`
   (перевірено grep), вони потрібні лише скриптам. Прибрати `activeusers` і `fileusers`; `currentuser` лишити,
   якщо потрібен для `h.checkpoint` (див. 2.2). Записати в CHANGELOG, що потрібен re-import плагіна.

### 1.5 Тести

- `tests/test_auth.py`: HTTP без токена/з неправильним/з правильним; WS без `hello`, з поганим токеном,
  rogue-клієнт з `Origin: null` не отримує `exec`; `compare_digest` використовується.
- Доповнити `tests/test_fuzz.py` сценаріями з невалідним токеном.
- `tests/test_queue.py`: переповнення черги → 503 і скрипт не виконано.

Готово, коли: веб-сторінка з `<iframe sandbox>` не може зареєструватися як плагін (ручний тест + автотест),
`pytest -q` зелений, `doctor` показує стан токена.

## Фаза 2. Безпечні записи → 2.5.0

### 2.1 Undo по одному exec

1. `plugin/code.js`: після кожного успішного або неуспішного exec викликати `figma.commitUndo()`,
   щоб Cmd+Z користувача відкочував рівно один скрипт агента, а не шматок.

### 2.2 Чекпоінти

1. Хелпер `await h.checkpoint(label)` → `figma.saveVersionHistoryAsync("figmosha: " + label)`.
2. Прапорець CLI `--checkpoint "<label>"` (JSON `checkpoint`): плагін робить чекпоінт перед виконанням.
3. Усі «масові» скрипти зі skills (фаза 5) роблять чекпоінт автоматично.

### 2.3 Атомарність — чесно

Plugin API не має транзакцій: скрипт, що впав посередині, лишає частину змін. На відміну від `use_figma`.

1. Задокументувати це у skill `figmosha-core` (фаза 5).
2. Правило для всіх хелперів фази 4: **спочатку валідація всього вводу, потім записи**.
3. Відповідь з помилкою містить `mutated: true/false` — плагін ставить прапорець при першому записі
   (обгортка над `figma.on("documentchange")` на час exec).

Готово, коли: тест у `tests/helpers.test.js` на порядок «валідація → запис», ручна перевірка Cmd+Z.

## Фаза 3. Ощадливий вивід і запуск скриптів за назвою → 2.6.0

Найбільший виграш у токенах.

### 3.1 Аргументи для exec

1. `/exec` приймає `args` (JSON). У плагіні він доступний як змінна `args`:
   `new Function("figma", "print", "h", "args", ...)`.
2. CLI: `figmosha exec --file x.js --args '{"name":"Color"}'` або `--args @spec.json`.

### 3.2 Бібліотека скриптів

1. Каталог `scripts/` у репо: кожен файл — один готовий сценарій, читає вхід лише з `args`.
2. Команда `figmosha run <name> [--args @file.json]` — знаходить `scripts/<name>.js`, шле його з `args`.
   Агент **не читає** тіло скрипту, лише його опис у skill.
3. `figmosha run --list` — назви й однорядкові описи (з першого рядка-заголовка в `scripts/<name>.json`
   поруч зі скриптом: `{"description": ..., "args": {...schema...}}`).
4. Валідація `args` за схемою на стороні CLI до відправлення (без зайвого round-trip у Figma).

### 3.3 Компактні відповіді

1. Прапорець `--brief` за замовчуванням для CLI-підкоманд: `tree` — глибина 2, без розмірів;
   `find` — лише `id name type`.
2. Хелпер `h.brief(nodeOrArray)` → `[{id, name, type}]`.
3. Ліміт розміру результату: `max_result` (за замовчуванням 8 KB для CLI). Понад це — обрізати
   і додати `truncated: {shown, total}`; повний результат лише з `--full`.
4. `figmosha exec` друкує тільки `result` (без обгортки), логи — тільки якщо є, помилка — коротко з `hint`.
   Повний JSON — `--raw` (вже є).

### 3.4 Скоротити AGENTS.md

1. AGENTS.md → ≤ 120 рядків: як викликати, `-T`, `run`, обов'язкові правила, посилання на skills.
2. Розділи про конкурентність, Windows, релізи, фази оновлення — у `docs/` та у skills
   (`figmosha-core`, `figmosha-maintainer`), які агент підвантажує лише на потребу.

Готово, коли: сценарій s1 з фази 0 виконується одним `figmosha run setup-tokens --args @s1.json`.

## Фаза 4. Хелпери для дизайн-систем → 2.7.0

Усі — upsert за назвою, спочатку валідація, повертають компактний звіт `{created, updated, skipped, errors}`.
Логіку брати з `figma-console-mcp` (`src/core/tokens-tools.ts`, `write-tools.ts`) та скриптів
`figma-console-mcp-skills` (MIT, з указанням авторства в `THIRD_PARTY_NOTICES.md`).

| Хелпер | Що робить |
|---|---|
| `h.tokens(spec)` | Колекції, режими, змінні (COLOR/FLOAT/STRING/BOOLEAN), аліаси `{color.blue.500}`, scopes, codeSyntax. Формат spec — W3C DTCG + власне поле `$modes`. |
| `h.exportTokens(collectionName?)` | Зворотний експорт у DTCG JSON. |
| `h.textStyles(spec)` | Текстові стилі з прив'язкою до змінних (розмір, line-height), автозавантаження шрифтів. |
| `h.effectStyles(spec)` | Тіні, blur. |
| `h.componentSet(spec)` | Набір компонентів з матриці варіантів: базова структура, auto layout, прив'язка кольорів і відступів до змінних, розкладка сіткою, властивості TEXT/BOOLEAN/INSTANCE_SWAP. |
| `h.arrange(componentSet, {gap, columns})` | Розкласти варіанти сіткою з підписами. |
| `h.bindAuto(root, map)` | Пройти дерево й прив'язати hex-кольори та числа до найближчих змінних за мапою. |
| `h.inventory()` | Компактний огляд файлу: колекції (назва, режими, к-сть змінних), стилі, компоненти (назва, к-сть варіантів, властивості). |
| `h.lint(root, rules)` | Незв'язані кольори/відступи, шари без auto layout, detached instances. |

Кроки:

1. Для кожного хелпера — специфікація spec і приклад у `scripts/*.json`.
2. Реалізація в `plugin/code.js` (бамп `PLUGIN_VERSION`, оновлення `tests/plugin_fingerprint.json`).
3. Тести на заглушці Figma в `tests/helpers.test.js`: парсинг DTCG, розв'язання аліасів, upsert без дублів,
   порядок auto layout, валідація до запису.
4. Живий тест: `tests/live_ds.py` на файлі `Figmosha Bench` (s1, s2), повторний запуск не створює дублікатів.
5. Відповідні готові скрипти: `scripts/setup-tokens.js`, `export-tokens.js`, `text-styles.js`,
   `component-set.js`, `inventory.js`, `lint.js` — тонкі обгортки над хелперами.

Готово, коли: сценарії s1 і s2 проходять одним-двома `figmosha run`, повторний прогін ідемпотентний.

## Фаза 6. Нові файли

Plugin API не вміє створювати файли; REST API теж ні. Плагін має бути запущений у кожному файлі вручну.

1. Спайк (1 день): перевірити, чи відкриває Figma Desktop новий файл за URL на кшталт
   `https://www.figma.com/design/new` / `figma://` і чи можна задати назву/проєкт.
2. Якщо так — команда `figmosha new "<назва>"`: відкриває новий файл, чекає (до 60 с), поки в ньому
   запустять плагін (`⌘⌥P`), повертає doc id для `-T`.
3. Якщо ні — задокументований шлях: файл створює людина або офіційний Figma MCP (`create_new_file`),
   далі робота через Figmosha.
4. Шаблони: `figmosha run bootstrap-file --args @template.json` — сторінки (Cover, Tokens, Components,
   Screens), базові токени, стилі.

## Ризики

- **Зміни Plugin API Figma** — dev-плагін з `new Function` залежить від поведінки Figma Desktop. Пом'якшення:
  `doctor` і живі тести `tests/live_*.py` перед кожним релізом.
- **Токен у `clientStorage`** доступний будь-якому скрипту, виконаному через бридж (той самий плагін).
  Прийнятно: хто може слати скрипти, вже знає токен.
- **Портовані skills розраховані на атомарність `use_figma`** — без адаптації (2.3) можуть лишати напівзроблені зміни.
- **Обов'язковий токен ламає наявні інтеграції** — тому м'який режим у 2.4–2.x і мажорна версія 3.0.0.
